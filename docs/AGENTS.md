# AGENTS.md — Moo 构建 · 部署 · 发布手册

> 面向在本仓库工作的 AI Agent 与人工维护者。
> 权威顺序：**本文件（流程与纪律）→ `docs/API.md` / `docs/Moo应用源协议.md`（接口与协议契约）→ 代码注释**。
> 若本文件与代码冲突：以代码为准，并回头修正本文件。
> 内容约定：本文件**不含**任何凭据、内网地址、主机名、私有路径与个人信息（见 §7）。

## 1. 项目速览

Moo = 飞牛 fnOS 上的第三方应用中心：浏览 / 安装 / 更新 / 卸载 / 通知，以 FPK 分发。

| 项 | 值 |
|---|---|
| 后端 | Go（**单二进制**；前端资源 `go:embed` 内嵌，无磁盘回退路径） |
| 前端 | React + TypeScript + Vite（`frontend/`） |
| 分发 | FPK；**默认只构建 x86**（双架构仅在发布需要时出） |
| 默认端口 | 38100 |
| 应用源协议 | `docs/Moo应用源协议.md`（`moo.json`：`schema_version` + `apps` + `releases`/`packages`） |
| 管理端鉴权 | 受信任通道 + 平台身份头；非 GET 变更请求另有自定义校验头（细节见 `docs/API.md`） |

## 3. 构建

```bash
bash build.sh x86      # 默认：只出 x86 包
bash build.sh all      # 双架构（仅发布需要时）
```

`build.sh` 会依次：

1. 由 `moo.json` 顶层生成本构建内嵌的发布说明 `internal/api/changelog_current.json`
   —— **要改更新日志就改 `moo.json`，不要改这个生成物**（它每次构建都会被重写）；
2. 可选刷新 `internal/reco/snapshots.json`（脚本网络失败时保留旧文件，属正常分支）；
3. 交叉编译：`-ldflags "-s -w -X main.Version=<version>"`；
4. 打 FPK（arm 包在 staging 内改写 manifest 的 `platform`，**不动源文件**）。

**版本号**：改 `fnos/manifest` 的 `version`，并同步 `moo.json` 自索引里的版本节点（两处都要动）。

**前端类型检查**：必须在 `frontend/` 目录内执行 `./node_modules/.bin/tsc -b`。
在仓库根直接 `npx tsc` 会拉到同名的无关包，得到假结果。

**产物验收**（不是"构建命令退出 0"就完事）：

- 退出码 0 + FPK 体积量级合理；
- 关键行为串确实在二进制里：用 `grep -ac <串> <二进制>`；
  **不要**用 `strings` 判定中文文案——UTF-8 中文会被整段漏掉，得到假阴性；
- FPK 内 `moo-server` 的 sha256 记下来，部署时要与运行态比对（§5.1）。
- ⚠️ **前端资源是 `go:embed` 内嵌、无磁盘回退**：改了 `frontend/` 必须**重建二进制**才生效，
  单换前端产物不会起作用；构建产物的文件名可直接当"前端是否真的改了"的指纹。
- 工具链版本以仓库现状为准（`go.mod`、`frontend/package.json`、构建脚本），**本文不写死版本号**（会过期）。

## 4. 提交前的本地门

```bash
gofmt -l <改动文件>                 # 必须干净
go vet ./internal/...
go test ./internal/... -count=1
go test -race ./internal/...        # 涉及并发 / 缓存 / 定时轮次的改动必跑
cd frontend && ./node_modules/.bin/tsc -b && npm run test:unit
```

纪律：

- **每条生产修复都要有「反向验证」**：临时回退这一条修复 → 对应用例必须 **FAIL** → 再复原，并用 `git diff` 自证源码已还原。
  没有"修复前必失败"的证据，就不算验证过。
- 新增鉴权 / 加密 / 缓存 / 并发相关改动，必须同时给出**安全面或一致性回归**断言。
- 断言写错比缺断言更危险：脚本/测试的期望值要与**当前设计**对齐（老断言过期时，先确认设计再改断言，不要为了让测试变绿而改产品）。

## 5. 部署到 fnOS（唯一正确姿势）

1. **备份数据目录**（配置 / 缓存 / 会话等）。归档运行中的日志可能触发"文件在读取时变化"，要么先停应用，要么以"归档可读"为判据。
2. `appcenter-cli stop moo`
3. **卸载但保留数据**：走平台卸载入口并明确选择"保留数据"。
   带「卸载向导」的版本，CLI 卸载会被拒绝 → 改用平台守护 socket 的卸载任务接口（同样指定保留数据）。
4. `appcenter-cli install-fpk -e <wizard.env> <fpk>`
   安装向导的字段必须由 env 文件提供（许可确认 / 访问端口 / 下载目录 / 日志路径）。
   ⚠️ **`install-fpk` 对已安装应用会直接报 "already installed"，没有升级子命令** → 换包 = 先卸后装。
5. `appcenter-cli start moo`
   若 CLI 报端口类错误而 HTTP 探测已可用，属于已知的 CLI 假错——**先探测再判定**。

### 5.1 部署后必查「四铁律」（缺一即视为部署失败）

1. **新 PID**，且进程可执行文件指向应用安装目录（不是旧进程 / 残留实例）；
2. **二进制 sha256 双侧一致**：FPK 内 `moo-server` == 运行态二进制；
3. **版本与前端指纹**：`/api/about` 的版本正确，且页面实际引用的 JS bundle 文件名与本次构建一致
   （bundle 名变了才说明前端真的换了）；
4. **数据零回归**：源数量、卡片数、已安装数、下载记录数、用户禁用集合 —— 与部署前**逐字**一致。

> ⚠️ **冷启动瞬态**：刚启动的头几秒目录尚未重建完成，此时采样会看到"源/卡数偏低、禁用集合为空"。
> 这不是数据丢失。**必须等目录重建完成再采样**；更稳妥的做法是先归档一份部署前基线，逐项比对。

### 5.2 回滚点

换包前必须留下可回滚的**数据归档**与**上一版 FPK**（若上一版来自用户分发渠道，也要留档），
并在报告里写明归档大小与可读性验证方式。

**回滚步骤**（沿部署同一条链路，只是换回旧包）：

1. 停止应用 → 卸载（**保留数据**）→ 安装上一版 FPK → 启动；
2. 若新版改动过数据 / 配置格式，恢复对应的**数据归档**（先备份当前状态，再覆盖）；
3. 按 §5.1 的四铁律复验（PID / 二进制 sha / 版本与前端指纹 / 数据逐字一致）；
4. 在报告里记录回滚时间点与验证结果。

> 兜底是**数据归档**，不要假设新版一定留了迁移路径——所以 §5 第 1 步的备份不可省。

## 6. 发布纪律（顺序不可颠倒）

```
实现 → 单测/静态门 → 本地 E2E → 构建 FPK → 交付用户验收
     → 双门（脱敏 + 独立审计） → 本地提交 + tag → 三端推送
```

- **未经用户明确指令，不做任何 git 提交或推送**（包括本地 commit）。
- **双门**缺一不可，且必须覆盖**本次全部**改动：
  - **门 1 脱敏**：全部待提交文件按敏感模式扫描，**0 命中**才放行；命中即修后重扫。
  - **门 2 独立代码审计**：范围核对（不得有批次外改动）、调试残留、硬编码、安全面（鉴权/加密/令牌）逐条复核；
    由**独立**的审计者给出 APPROVED / REJECTED，**不得自审自批**。
- **变更集一旦变化，双门必须重跑**（旧审计结论不可复用）。
- 更新日志三处同源：仓库自索引 `moo.json` ↔ 构建内嵌（关于页）↔ 平台 release 正文；文案由用户定稿。
- 自索引约定：`apps.moo.releases` **只保留最近 2 个版本**。
- CI：推送 tag 触发 Release 工作流；其 `gate` 任务执行整树脱敏扫描 + `go vet` + `go test`，**gate 红不得发布**。
- 同版本号重复打包：老用户不会看到更新提示（更新判定按版本号比较），发布时要确认这是预期行为。

**「改版本号」的完整同步清单**（漏一处就会出现版本对不上）：

| # | 位置 | 改什么 |
|---|---|---|
| 1 | `fnos/manifest` | `version`（构建产物的版本号来源） |
| 2 | `moo.json` 自索引版本节点 | 新增版本条目；`releases` 只留最近 2 个 |
| 3 | `moo.json` 的 packages | **重打 FPK 后**的 `sha256` 与 `size`（每次重打都会变） |
| 4 | 构建内嵌更新日志 | 由 `moo.json` 顶层生成——改 `moo.json` 即可（见 §3） |
| 5 | 平台 release 正文 | 与上者同一文案 |
| 6 | `README.md` | 版本徽章与能力清单 |

> 操作顺序：改 1–2 → 构建 → 用**新包的实测值**回填 3 → 再核对 4–6 三处同源。

## 7. 脱敏与仓库卫生（硬规则）

**绝不入库**：

- 任何真实凭据：口令、令牌、私钥、会话文件、带凭据的连接串；
- 内网地址与内网主机名 → 用文档保留段（如 `192.0.2.0/24`）与 `example.com` 代替；
- 个人邮箱 / 账号标识 / 个人设备信息；
- 运行期私有路径、日志、备份归档、数据库文件；
- 会话与构建产物：`*_TODO.md`、临时分析稿、截图、`build/`、`*.fpk`、`dist/` 等（按 `.gitignore`）。

**提交方式**：显式列出文件清单逐个 `git add`；**禁止 `git add -A`**（会把产物与临时文件一起带走）。

**测试夹具**：一律使用保留网段与示例域名。发现历史提交夹带敏感值时：
**停下来报告**，按约定流程处理，**不要静默改写历史**。

**提交前自检**：把"这批文件里有没有我不希望公开的字符串"当成一个必须执行的步骤，
而不是靠记忆；扫不干净就不提交。

**提交后抽检**：推送后用**未登录 / 匿名**方式回读一两个文件，确认公开面看到的内容与预期一致
（镜像与 CDN 可能有短暂缓存滞后，稍后重试即可；若持续不一致才视为异常）。

**范围要覆盖全**：文档、截图、示例配置、报错文案、测试夹具与 release 正文，**都算公开面**，
不能只扫源码。细则见 §12。

## 8. 技术史里程碑（能力视角）

> 细化到每个版本的变更，以 git tag 与仓库自索引 `moo.json` 的 changelog 为准。

| 阶段 | 关键能力 |
|---|---|
| 0.1–0.2 | **立项**：clean-room 重写；Go 单二进制 + 内嵌前端；多来源聚合（第三方 JSON 源 / 社区源 / 官方目录）；FPK 打包与自更新链路 |
| 0.2x–0.3x | 通知体系（多渠道、多呈现档位、去重与冷却）；加速源测速与自动优选；应用详情（README / 预览 / 更新日志）；内存与性能治理（目录缓存、预算化刷新、SWR、体缓存 + ETag） |
| 0.3x–0.4x | 双端体验（桌面 / 移动）；安装·配置·卸载向导；日志页与轮转；备份与恢复；Docker 加速源接管；目录去重档位 |
| 0.5x–0.6.2x | 面板免登录改造（平台授权 scope）；官方目录与第三方源合并；深链与恢复门（去跳闪）；三种视图（标准 / 极简 / 极光）；安装位置遵循系统设置；多卷与多架构识别 |
| 0.6.3xx | **溯源与更新治理**：应用级"禁用"；上游溯源（含"整仓 fork 搬运"判定与显示名/版本口径）；更新策略四档（严格 / 友好 / 宽松 / 强制上游）；上游自动纠正；源重合率只读信号；"添加为源"可加性预探测 |

## 9. 反复踩到的坑（动手前先读）

1. **构建源树必须在持久目录**：只在临时目录里活过一次的源码，等于已经丢了。
2. **打包前校验"产物内容本身"**：只看 `git status` / `git diff` 没有意义（构建产物常被 gitignore 忽略，零验证价值）。
3. **UI 暴露了能力 ≠ 后端接了线**：新增设置项/按钮，要配「枚举契约测试」——前端每个取值 × 后端每个分支全覆盖。
4. **默认值最容易被漏测**：用户常点的是非默认项，默认分支可能从未被执行过。
5. **单一环境会掩盖多环境缺陷**：单卷、单架构、单一主题下不存在的 bug，换环境就会冒出来；能上真机的别只信模拟。
6. **缓存 / 竞态类改动先定位再修**：证据不一致（一边复现、一边复现不了）时，先写**决定性最小实验**，不要盲改。
7. **凡"改态 → 验证 → 还原"的测试，必须在同一脚本内闭环**（含快照与还原断言），否则中断一次就留下脏状态。
8. **E2E 不得清空用户真实数据**：脚本只允许清理**自己创建**的测试键；跑前快照、跑后逐字比对，不一致即失败。
9. **上游接口可能有短期频率限制**：被拒时不要循环重试（可能把自己锁住一段时间），改用退避并在日志里留痕。
10. **同一错误连续出现 3 次就停手**：换方案或先写清卡点，不要用同一方法反复撞。
11. **长链路任务要分段**：上下文会被过程日志撑爆；把重活派给独立执行者、结论落文件、主流程只收摘要。
12. **先确认"改哪棵树"**：多个工作树 / 副本并存时，凭印象改很容易落到已废弃的那棵上（改到死代码）。动手前用构建路径或分支名确认目标。
13. **临时目录里的证据会消失**：`/tmp` 一类位置的内容会被环境清理；需要留档的日志、抓包、截图一律落到项目目录，并把路径写进报告。
14. **长命令链首段失败时，先查现状再决定重跑**：`ps` 看有无残留进程、看远端与产物是否已生成——盲目重跑会重复建 tag / release 或覆盖已上传的资产。
15. **两种统计口径可能互斥**：同一条命令里混用会静默无输出（例如 `du -s` 与 `--max-depth`），下结论前先确认工具语义。
16. **远端 API 的字段层级容易记错**：同一语义在不同平台可能位于不同层级（如提交标识可能在 `commit.id` 或 `tag.id`，树对象可能在 `commit.tree` 的嵌套层）。取值前先看一次真实响应结构，别按记忆写解析。
17. **"产物没变"与"构建没跑"要分清**：前端构建产物文件名可直接当指纹——文件名未变说明本次确实没有前端改动；但要与"构建根本没执行到那一步"区分开，否则会把失败误判为"零改动"。

## 10. 数据与安全边界

- **生产设备上的用户数据不是测试场**（源配置、禁用/忽略记录、安装状态、下载记录）。
  优先在**独立实例**（独立数据目录 / 端口 / socket）+ **假源**上验证，再对生产做**只读**核对。
  **起独立验证实例的做法**（对生产零影响）：另建一套数据目录与端口（含 socket 路径），
  用**构造的假源 / 假应用**喂数据，源地址一律指向本地假源；验证完销毁实例，不留残留进程与端口占用。
- 管理端接口只在受信任通道 + 身份头下可用。**不要**为了调试给调试通道开放管理权限，
  **不要**在前端硬编码任何凭据，**不要**把内部令牌写进日志。
- 任何改动都不得放宽既有鉴权；新增接口要同步更新 `docs/API.md` 与镜像文档（二者需保持一致）。
- 涉及用户数据的操作要可回滚：先备份、再操作、后比对。

## 11. 协作与续接协议

面向"多个执行者（人 / AI 会话）接力"的场景，避免重复劳动与状态丢失。

**任务清单**：非平凡任务先在仓库根建 `<SLUG>_TODO.md`（已在 `.gitignore` 覆盖范围内，见 §7），
用 `- [ ]` / `- [x]` 记录步骤；每步**真正做完**立刻勾选，不要批量勾。

**长任务状态**：超过约 20 步、或跨多文件的任务，另建 `PROGRESS.md` 记录
「已完成 / 下一步 / 已知问题 / 产物路径」，**接手者先读它再动手**。

**接手的第一个动作**：若任务涉及一台"正在运行的设备"，先检查有没有**未还原的测试态**
——被改过的配置、指向假地址的源、残留的进程或端口占用。历史上出现过"上一棒没跑完还原
步骤就中断"，导致假状态长期驻留。

**汇报格式**：结论 + 产物路径 + 关键数字，控制在十行以内；过程细节写进文件，
不要把构建日志或整份文件内容贴进对话。

**接力边界**：一个执行者产出的"对外交付物或系统变更"，应由**另一个执行者复核**后再对外交付
——至少确认产物在场、验收命令的实际输出、以及变更差异或回滚点。只读的检索与分析可免复核。

**停手规则**：同一错误连续出现 3 次，立刻停止原方法重试，换方案或写清卡点后报告。

## 12. 安全暴露面（文档 / 截图 / 日志同样算）

仓库不只有代码：文档、截图、示例、报错文案、测试夹具、release 说明**都是公开面**。

| 类别 | 不得出现 | 替代写法 |
|---|---|---|
| 网络标识 | 内网地址、内网主机名、内部端口分配、设备标识 | 文档保留段（如 `192.0.2.0/24`）、`example.com` |
| 管理通道细节 | 具体身份头名、内部路径前缀、管理端点路径、令牌形态 | 抽象表述；细节只在 `docs/API.md`（该文件同样受本表约束） |
| 平台与账号 | 面板账号、登录口令、访问令牌、个人邮箱、个人设备名 | 一律不写；凭据只存在于运行期配置 |
| 运行数据 | 真实通知渠道、下载记录、目录快照、日志原文 | 脱敏样例或构造数据 |

**三条硬约束**：

1. **调试通道默认不受信任是设计，不是缺陷** —— 不得为了让本地调试"能调管理接口"而放宽鉴权。
2. **凭据零前端、零日志**：不在前端硬编码凭据；不把令牌 / 口令回显进日志或错误消息。
3. **截图与录屏入库前逐张目检**：地址栏、通知渠道配置、用户数据列表、日志行都可能带出敏感值。

**自查动作**：把这批文件里"有没有我不希望公开的字符串"当成一个**必须执行的步骤**（见 §7），
而不是靠记忆与自信。
